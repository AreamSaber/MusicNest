# 鸿音管家（HarmonySound）产品需求文档 (PRD)

> 版本：v1.0 | 日期：2026-06-12 | 作者：毕设项目组

---

## 一、项目概述

### 1.1 项目背景

传统中小型乐器租赁门店运营中存在以下核心痛点：

1. **租赁流程低效**：依赖纸质单据或微信聊天记录，信息分散、易出错，客户无法实时查看可租乐器和订单状态
2. **售后维修缺乏追踪**：用户报修后往往石沉大海，维修进度不透明，客户满意度低
3. **库存状态不透明**：门店难以实时掌握每件乐器的"可租/已租/维修中/报废"状态，调度效率低下
4. **经营决策缺数据**：缺少营收统计、热门品类分析、客户画像等数据支撑，定价和采购依赖经验而非数据

### 1.2 项目目标

开发"鸿音管家"——一款覆盖乐器租赁与售后全链路的管理平台，包含：

- **鸿蒙端 App**：面向租琴用户，提供乐器浏览、在线租赁、订单跟踪、售后报修等功能
- **Web 管理后台**：面向门店员工与管理员，提供订单审批、库存管理、工单处理、数据看板等功能
- **后端服务**：基于 Spring Boot 的统一 RESTful API，支撑两端业务

实现从"选琴 → 租赁 → 使用 → 报修 → 归还 → 复购"的完整业务闭环。

### 1.3 产品定位

| 维度 | 说明 |
|------|------|
| 目标用户 | 乐器租赁门店的客户（C端）与门店运营人员（B端） |
| 核心价值 | 一站式乐器租赁与售后管理，提升运营效率与客户体验 |
| 平台特色 | 鸿蒙原生体验 + 智能推荐 + 信用评估体系 |
| 终端形态 | 鸿蒙 App（手机端）+ Web 管理后台（PC端） |

## 三、功能需求详述

### 3.1 鸿蒙端（C端 — 普通用户）

---

#### F-01 用户注册与登录

| 项 | 内容 |
|----|------|
| **优先级** | P0（必做） |
| **描述** | 用户通过手机号验证码注册/登录，或使用华为账号一键登录 |
| **输入** | 手机号、短信验证码 |
| **输出** | JWT Token，跳转首页 |
| **业务规则** | ① 验证码有效期为 5 分钟，每日最多发送 10 次；② 首次登录自动注册；③ 华为账号登录需用户授权后可获取手机号和个人信息；④ Token 有效期 24 小时，支持 Refresh Token 续期 |
| **异常处理** | 验证码错误提示、发送频率超限提示、网络异常提示 |

#### F-02 个人资料管理

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **描述** | 查看和编辑个人资料 |
| **输入** | 昵称、头像（可选）、联系方式 |
| **输出** | 更新后的用户信息 |
| **业务规则** | 昵称长度 2-20 字符，头像支持拍照/相册选取 |

#### F-03 实名认证

| 项 | 内容 |
|----|------|
| **优先级** | P1 |
| **描述** | 上传身份证正反面照片，填写真实姓名与身份证号 |
| **输入** | 真实姓名、身份证号、身份证正反面照片 |
| **输出** | 认证状态（待审核/已通过/已驳回） |
| **业务规则** | ① 姓名与身份证号需与照片 OCR 结果一致；② 认证通过后方可租赁；③ 未认证用户不可下单 |

#### F-04 信用分体系

| 项 | 内容 |
|----|------|
| **优先级** | P1 |
| **描述** | 展示用户的信用评分、等级及影响因素明细 |
| **输入** | 系统自动计算 |
| **输出** | 信用分（0-1000）、信用等级（优秀/良好/一般/较差）、各维度得分明细 |
| **业务规则** | 模型维度：① 履约率（按时归还占比，权重 40%）；② 逾期记录（逾期次数与天数，权重 25%）；③ 评价得分（租赁评价平均分，权重 15%）；④ 租赁活跃度（累计租赁次数，权重 10%）；⑤ 账户完整度（实名认证、资料完善度，权重 10%）。信用等级映射：≥800 优秀 → 押金减免 30%；600-799 良好 → 押金标准；400-599 一般 → 押金上浮 20%；<400 较差 → 限制租赁 |

#### F-05 乐器浏览与搜索

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **描述** | 分类浏览乐器、搜索、筛选、查看详情 |
| **功能点** | ① 首页：推荐位（轮播图）+ 分类快捷入口 + 热门乐器列表；② 分类浏览：钢琴/吉他/提琴/管乐/民乐/打击乐，每类展示乐器卡片；③ 多维筛选：品牌、价格区间（滑块）、成色（全新/95新/9成新/8成新）、适用人群（入门/进阶/专业）；④ 关键词搜索：搜索乐器名称、品牌；⑤ 乐器详情：轮播图、名称/品牌/型号/成色/规格参数、租金价格阶梯（日租/周租/月租价格）、库存状态、用户评价列表 |
| **业务规则** | ① 库存为 0 的乐器标注"已租罄"，不可下单；② 租金价格阶梯由管理员在后台配置；③ 支持下拉刷新和上拉加载更多 |

#### F-06 智能推荐

| 项 | 内容 |
|----|------|
| **优先级** | P1 |
| **描述** | 基于用户画像，通过大模型 API 生成个性化乐器推荐 |
| **输入** | 用户画像（浏览历史、租赁历史、偏好标签） |
| **输出** | 推荐乐器列表（3-6 件），每件附带推荐理由 |
| **业务规则** | ① 新用户（无历史数据）展示热门乐器作为冷启动策略；② 有历史用户：构造 Prompt（用户画像 + 库存可租乐器列表）→ 调用大模型 API → 解析返回的乐器 ID 列表 → 加载对应乐器信息展示；③ 推荐模块位于首页"猜你喜欢"区域；④ 推荐结果缓存 2 小时，避免频繁调用 API；⑤ 用户可对推荐结果点击"不感兴趣"进行简单负反馈 |
| **技术说明** | 使用大模型 API（如 OpenAI / 国内模型）的 Chat Completion 接口，通过精心设计的 System Prompt 和 User Prompt 引导模型输出结构化推荐结果 |

#### F-07 租赁下单

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **描述** | 用户选择乐器、租期，确认订单并支付押金 |
| **流程** | 乐器详情 → 点击"立即租赁" → 选择租赁时长（起租天数/起租周数/起租月数）→ 系统计算押金与租金 → 确认订单页（乐器信息、租期、押金额、租金、配送方式）→ 支付 → 下单成功 |
| **业务规则** | ① 实名认证通过方可下单；② 同一用户同时最多租赁 3 件乐器；③ 押金 = 乐器价值 × 押金比例 × 信用折扣；④ 租金 = 日租金 × 租期天数，周租/月租有折扣系数；⑤ 下单后 30 分钟内未支付则自动取消；⑥ 下单即锁定库存（状态变更：可租 → 已租；管理员审核不通过时回滚为可租）；⑦ **支付说明：本系统为毕设项目，支付模块采用模拟实现，点击支付后系统直接标记支付成功，不接入第三方支付网关。论文中设计了完整的支付接口规范（见 SPEC §4.3.4），可扩展对接真实渠道** |

#### F-08 订单管理

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **描述** | 查看所有订单、跟踪订单状态 |
| **功能点** | ① 订单列表（Tab 切换：全部/进行中/已完成/已取消）；② 每项展示：乐器缩略图、名称、租期、金额、状态标签；③ 订单详情：完整信息 + 状态时间轴（下单→支付→发货→使用中→归还→完成）；④ 进行中的订单支持"续租"和"归还预约"操作 |

#### F-09 续租申请

| 项 | 内容 |
|----|------|
| **优先级** | P1 |
| **描述** | 对进行中的订单申请延长租期 |
| **输入** | 续租天数/周数 |
| **输出** | 续租订单（关联原订单），待支付续租费用 |
| **业务规则** | ① 仅"租赁中"状态可续租；② 续租租金按原订单单价计算；③ 续租需管理员审核确认 |

#### F-10 归还预约

| 项 | 内容 |
|----|------|
| **优先级** | P1 |
| **描述** | 用户预约归还时间 |
| **输入** | 预约归还日期 |
| **输出** | 预约成功，订单状态变为"待归还" |
| **业务规则** | 预约日期不能早于当前日期，最晚可预约租期结束前 7 天内；超期未预约归还的用户需先归还再重新租赁 |

#### F-11 售后报修

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **描述** | 用户对租赁中的乐器发起报修 |
| **流程** | 选择订单 → 描述故障（文字）→ 拍照上传（1-5 张）→ 选择紧急程度（普通/紧急）→ 提交 |
| **业务规则** | ① 仅"租赁中"订单可报修；② 报修提交后生成工单，状态为"待派单"；③ 紧急报修在工单列表中置顶标记 |

#### F-12 维修进度跟踪

| 项 | 内容 |
|----|------|
| **优先级** | P0 |
| **描述** | 以时间轴形式展示维修工单的完整流转过程 |
| **展示内容** | ① 提交报修；② 门店接单/派单；③ 维修中；④ 维修完成待验收；⑤ 用户验收确认；⑥ 完成。每步显示时间、操作人、备注 |

#### F-13 评价

| 项 | 内容 |
|----|------|
| **优先级** | P1 |
| **描述** | 对已完成的租赁订单和维修工单进行评价 |
| **输入** | 评分（1-5 星）、文字评价、可选图片 |
| **业务规则** | ① 订单完成后 30 天内可评价；② 评价后不可修改；③ 评价数据计入信用分和乐器评分 |

## 四、非功能性需求

### 4.1 性能要求

| 指标 | 目标值 |
|------|--------|
| API 响应时间（P95） | ≤ 500ms（查询），≤ 1000ms（写入） |
| 鸿蒙端页面首屏加载 | ≤ 2s |
| Web 端列表页加载 | ≤ 1.5s |
| 并发用户支撑 | ≥ 50（模拟环境） |

### 4.2 安全要求

| 要求 | 实现方式 |
|------|----------|
| 接口鉴权 | JWT Token，所有非公开 API 需携带 Token |
| 密码存储 | BCrypt 加密，不可逆 |
| SQL 注入防护 | MyBatis-Plus 参数化查询 |
| XSS 防护 | 前端输出编码，后端输入校验 |
| 敏感数据脱敏 | 手机号、身份证号在日志中脱敏 |
| 验证码防刷 | 同一手机号每分钟最多 1 次，每日最多 10 次 |

### 4.3 兼容性要求

| 终端 | 要求 |
|------|------|
| 鸿蒙端 | HarmonyOS NEXT API 12+，手机设备 |
| Web 端 | Chrome 90+、Edge 90+ |

### 4.4 可用性要求

- 鸿蒙端支持屏幕朗读（无障碍）
- Web 端支持键盘导航
- 所有错误操作有明确提示
- 关键操作（删除、退款）有二次确认

## 五、UI/UX 设计方向

### 5.1 设计语言

| 维度 | 鸿蒙端 | Web 管理端 |
|------|--------|------------|
| 设计规范 | HarmonyOS Design | Ant Design / Element Plus 风格 |
| 主色调 | 深蓝紫渐变 #4A3AFF → #6B5CFF | 同色系，深色侧边栏 |
| 圆角 | 卡片 16px，按钮 8px | 卡片 8px，按钮 4px |
| 导航 | 底部 Tab（首页/分类/订单/我的） | 左侧菜单栏 + 顶栏 |
| 动效 | 点击缩放、滑动渐现 | 页面切换过渡 |

### 5.2 鸿蒙端页面结构

```
底部 Tab 导航
├── 首页（推荐位 + 分类入口 + 猜你喜欢）
├── 分类（乐器分类浏览与筛选）
├── 订单（订单列表 + 状态跟踪）
└── 我的（个人资料 + 信用分 + 报修记录 + 评价提交 + 我的评价 + 续租/归还预约 + 设置）
```

### 5.3 Web 端导航结构

```
左侧菜单栏
├── 工作台（概览页）
├── 订单管理
│   ├── 订单列表
│   └── 逾期处理
├── 库存管理
│   ├── 乐器列表
│   └── 入库登记
├── 工单管理
│   └── 工单列表
├── 数据看板（仅管理员可见）
└── 系统管理（仅管理员可见）
    ├── 员工管理
    └── 系统配置
```

## 六、验收标准

### 6.1 核心流程验收

| 场景 | 验收标准 |
|------|----------|
| 用户注册登录 | 手机号接收验证码 → 输入 → 登录成功，进入首页 |
| 浏览与搜索 | 分类浏览乐器 → 筛选 → 查看详情，信息完整 |
| 租赁下单 | 选择乐器 → 选租期 → 确认 → 支付 → 下单成功，库存扣减 |
| 订单跟踪 | 订单列表查看 → 详情时间轴展示正确 |
| 售后报修 | 提交报修 → 生成工单 → 工单状态更新可见 |
| 员工审核订单 | 登录后台 → 查看待审核 → 通过/驳回 → 状态联动 |
| 工单流转 | 派单 → 维修中 → 待验收 → 完成 |
| 管理员看数据 | 登录后台 → 数据看板 → 图表正确展示 |
